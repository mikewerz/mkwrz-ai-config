# Agentic Software Factory V3

## Decision

V3 replaces the fixed delivery pipeline with a small, durable workflow engine while preserving the successful agent interaction contract:

> The tracker decides which durable node is active. A full-capability agent decides how to achieve an agent node and explicitly calls back with its outcome.

The tracker is the control plane and source of truth. Supervisors remain generic executors near repositories and Herdr sessions. Herdr lifecycle is observational and never advances a workflow.

For practical workflow YAML, node I/O, and reusable-prompt guidance, see the [Workflow and Prompt Authoring Guide](../workflow-and-prompt-authoring.md).

## Artifacts

Artifacts live beneath `TICKETS_ROOT`:

```text
tracker-config.yaml
prompts/
  <prompt-id>.md
  .versions/<prompt-id>/<sha256>.md
workflows/
  <workflow-id>.yaml
  .versions/<workflow-id>/<sha256>.yaml
<ticket>.md
```

Prompts are independently reusable Markdown artifacts. Workflows reference prompt IDs. Every saved revision is content-addressed and retained. A ticket pins a workflow revision when it is created or when an operator explicitly migrates it; edits to a workflow never silently alter running work.

## Workflow definition

A workflow is a directed graph with one start node and a configurable transition ceiling. Node IDs are stable within a revision. Workflow definitions also declare typed ticket inputs and ordered display stages.

Inputs are Boolean or select values with labels and defaults. Nodes may compare one declared input to one literal value and follow an explicit `otherwise` target when the comparison is false. The engine never evaluates source code or a general expression language.

Stages group nodes for the ticket UI and declare an operational role: specification work, delivery work, independent review, or terminal. This role projects the active workflow node into the coarse `phase` and `status` fields retained for storage and filtering; it does not select a provider, conversation, prompt, PR rule, or GitHub-follow-up route. A stage is either required or ticket-configurable. Configurable stages declare their default and one explicit bypass target. Tickets persist their input values and enabled-stage selections in Markdown. Required stages cannot be disabled through ordinary ticket controls.

Supported node types are:

- `agent`: sends a reusable prompt through the existing supervisor/Herdr handshake. It declares an agent-profile alias (or legacy provider role), conversation key, and typed outcomes containing an ID, label, description, and target.
- `script`: runs either a configured script file or trusted inline shell, Python, or JavaScript on a supervisor and routes its numeric exit code through declared mappings. Executable resolution and process working directory are separate, explicit settings. It may persist stdout separately and place a configured tail into the next transition context.
- `human_gate`: waits for one of its declared human choices. Each choice contains an ID, label, description, target, and optional required-comment policy.
- `read`: exact-matches one ticket metadata value against declared JSON values and follows an explicit default route.
- `write`: atomically replaces one ticket metadata value and follows its single declared target.
- `workflow`: invokes a pinned child workflow and routes the child's numeric terminal status code when the child returns.
- `fan_out`: copies its incoming transition context into two or more declared branches. V3 executes those branches sequentially under the ticket's single durable lease/ownership model.
- `fan_in`: waits until every branch declared by its fan-out has arrived, combines their summaries, prompt outputs, and output-log references, and follows one target.
- `terminal`: completes, fails, or cancels the top-level ticket, and returns a numeric status code when reached inside a child workflow.

The tracker configuration defines a default agent-profile alias and named aliases, each resolving to a provider, exact model, and reasoning setting. Agent nodes select an alias; the resolved tuple is pinned into the ticket with the workflow revision and passed to the provider's native CLI on launch/resume. Changing an alias affects future tickets, not work already pinned. Legacy nodes may still use `provider: work`, `provider: review`, or an explicit Claude or Codex provider. The current node's pinned resolved profile and `conversation_key` are authoritative. Conversation records keyed by that key own Herdr pane/session continuity independently of graph shape, so one workflow revision cannot assign the same conversation key to incompatible selectors. If an older stored conversation names a different resolved provider, claiming the node clears its machine-local pane/session references instead of resuming the wrong provider. The old phase-agent fields are display projections only for V3 tickets and cannot invalidate a V3 lease.

An agent node may declare `pull_request_requirement` with a PR phase and either `scope: any` or `scope: primary`. The tracker enforces that contract on completion. PR requirements are never inferred from node IDs or prompt names, so nodes may be renamed or reused without weakening completion guarantees.

`skipped` is not a callback outcome. When a condition is false or a configurable stage is disabled, the tracker records an engine-owned `bypassed` node run and follows the declared `otherwise` or stage bypass target. Agents and humans never need to know or submit a magic skip string. Legacy `condition` and `on` YAML is normalized when read; unchanged shipped defaults may be upgraded, while custom workflow content remains operator-owned.

Every declared route may also carry `metric_class: success | failure | neutral`. This classification is analytics metadata, not control flow: route IDs remain stable workflow contracts and the engine never guesses success from their spelling. Unclassified custom routes remain valid and are reported separately until an operator classifies them. Engine-owned bypasses, interruptions, and lease losses are operational dispositions rather than successes or failures.

## Runtime and fencing

Mutable runtime belongs to the ticket, not the workflow definition. The ticket records:

- pinned workflow ID and revision;
- current node;
- transition count, per-node visit counts, and per-node attempt/loss counters;
- immutable node-run records;
- active lease and node-run ID;
- reusable conversation references keyed by conversation key.
- typed workflow input values, enabled-stage selections, and the transition context entering the current node.
- JSON-compatible ticket metadata, pinned child-workflow revisions, resolved agent profiles, nested-workflow call frames, and in-progress fan-out frames.

Every visit creates a node run containing the workflow revision, node ID/type, visit and attempt numbers, supervisor/provider, timestamps, input snapshot digest, outcome, summary, optional handoff, and reported artifacts. Every graph move uses the same transition operation, which replaces incoming context and records its source, target, outcome, summary, handoff, actor, timestamp, visit, and resulting node state. Agent and activity callbacks are fenced by lease and node-run ID. Stale callbacks cannot move the graph.

Lease-loss escalation is scoped to the current node rather than its projected phase. Any accepted agent or Script callback resets that node's consecutive-loss count. The first two unexplained losses return the same node to ready; the third blocks it for operator attention without contaminating other nodes in the same phase.

Loops are ordinary explicit edges. Execution stops for human attention when a node exceeds its `max_visits` or the workflow exceeds `max_transitions`. These are orchestration safety limits, not judgments about agent quality.

## Agent nodes

The existing interaction is retained:

1. A supervisor claims a ready agent node.
2. It writes a supervisor-local durable assignment bundle for that exact node run.
3. It starts or resumes the ticket conversation in Herdr and sends a small bootstrap containing the exact `START_HERE.md`, project-root, and callback-helper paths.
4. The agent works with its normal tools and permissions.
5. The agent may comment, ask one or many questions, complete with a declared outcome plus summary and optional handoff, or fail.
6. The tracker records the node run and follows the matching edge.
7. The next node-run bundle renders the incoming node, outcome, summary, handoff, configured Script-output tail, and link to any full output artifact. It also documents lease-fenced metadata read/write callbacks. Reusable node prompts may reference the same metadata tags.
8. The agent stops. Herdr idle/done without a callback causes at most one callback reminder and never advances the workflow.

Starting an agent in a newly created pane or restoring one into a saved pane may briefly fail while a macOS login shell initializes. The supervisor retries only Herdr's `agent_pane_busy` startup error at 500-millisecond intervals for at most 10 seconds. Other errors fail immediately, and exhausting the retry window returns the original Herdr failure without advancing or failing the workflow semantically.

The bundle lives beneath the supervisor's configurable `ASSIGNMENT_ROOT` as `<supervisor-id>/tickets/<ticket-id>/runs/<attempt>-<node-id>-<node-run-id>/`. It contains `START_HERE.md`, `ticket.md`, `node.md`, `incoming.md`, `context.json`, `callbacks.md`, `callbacks.json`, an executable `callback` helper, `updates/`, and `outbox/`. A ticket-level `ACTIVE.json` points to the current run. IDs are used directly in directory names rather than normalized. A quota pause retains the same run; a retry or later loop visit creates a new run directory.

The files are recovery snapshots, not a second control plane. Agents are told that edits may be useful as scratch notes but are not observed by the supervisor and never mutate the authoritative ticket, workflow, or callback contract. No permission profile, read-only mount, watcher, or sanitizing filename layer is introduced. Tracker callbacks and APIs remain authoritative.

The generated callback helper owns the concrete schemas and lease URLs for comment, batched questions with answer options, completion, failure, and metadata reads/writes. It validates the selected completion outcome, sends the request, and records a local request/response pair. `START_HERE.md` tells the agent where to read the full contract and how to print a schema example. This is a plain generated executable, not a skill.

The default assignment prompt is intentionally only a bootstrap. The durable files separate incoming transition context, the current-node contract, and the callback protocol. Reusable prompts tell agents to choose an exact declared outcome ID, use `summary` as the node's durable record, and use `handoff` only for actionable context needed by the next node. Reusable prompts cover specification, implementation, review, Postman baseline design, non-production validation, rollback, merge, and release-ticket creation while leaving execution strategy to the full-capability agent.

Live guidance, question answers, and live-ticket edits refresh the current ticket and node snapshots first, then create an ordered Markdown file beneath `updates/`. The follow-up Herdr message contains the exact update, `START_HERE.md`, and callback-helper paths. If Herdr becomes idle or done without a terminal callback, the single reminder repeats the exact absolute `START_HERE.md` and helper paths; it never assumes the initial message survived compaction.

The durable node instructions deny merging by default unless the current node prompt explicitly authorizes it. The reusable `merge.md` prompt is that authority in the shipped Dev Only workflow: it requires a still-applicable preceding human approval, passing protections, mergeability, and no newer invalidating feedback. There is no separate merge-permission field in workflow YAML or the UI.

Review remains an independent conversation and role, not a restricted sandbox. Workflow authors select a separate conversation key and may use an opposite-provider profile alias when independent-provider review is required.

## Harness telemetry and ticket cost

Usage observation uses a versioned provider-neutral snapshot rather than adding provider fields to the ticket schema. Each snapshot identifies its harness and native session, exact observed model IDs, reasoning setting plus provenance, normalized input/cache-write/cache-read/output/reasoning token counts, cost value plus `reported | estimated | unavailable` provenance, context use, rate-limit windows, and scalar harness attributes. Built-in Claude and Codex adapters are registered behind the same interface; future harnesses add an adapter without changing tracker storage or UI contracts.

Every agent node records a baseline snapshot and latest snapshot. The tracker, not the supervisor or provider adapter, derives non-negative node deltas. A new native conversation starts from a zero baseline; a reused conversation starts from its cumulative usage when that node begins. This makes durable node runs independently aggregable without double-counting earlier nodes in the same conversation. The active execution and matching node run are updated together on heartbeat. Because an agent may call `complete` immediately before its final session record is flushed, `POST /api/work/{lease}/telemetry` may update the retained node run by lease ID after the execution lease has closed, but can never transition the workflow.

Each node run also owns a provider-neutral timing ledger. Heartbeats accrue active runtime, human gates accrue human-wait time from node entry through the decision, and an exhausted harness rate-limit window with a future reset accrues quota-paused time while the supervisor continues heartbeating the lease. If a five-hour Claude or Codex limit expires between heartbeats, accounting splits the interval at the declared reset timestamp and resumes active time automatically. Wall time remains separately derivable from the run timestamps. Ticket token, cost, active-time, quota-pause, human-wait, and elapsed totals are derived from durable node runs so repair loops and repeated visits are included without storing a second rollup that can drift.

The dashboard displays live and per-node metrics and computes ticket totals from node deltas. It always states coverage. Harness-reported cost is shown as reported; price-table calculations, if added later, must be labeled estimated and retain their pricing source/version. Missing subscription cost remains unavailable rather than being treated as zero. Telemetry collection is best effort and cannot block, fail, or complete agent work.

## Factory metrics and production assessment

The tracker derives analytics from authoritative Markdown and immutable node-run history without adding a database in V3. Reports group workflows by both ID and pinned content revision so an edited workflow never blends structurally different nodes into one success rate. Node reports include classified success/failure/neutral/unclassified outcomes, branch frequency, wall/active/human-wait/quota-pause time, interruptions, bypasses, lease losses, token/cost totals, and coverage. Agent comparisons use the ticket-pinned profile alias plus resolved provider, model, and reasoning tuple.

Platform reports include ticket, token, known-cost, active-time, quota-pause, and human-wait totals plus five-number summaries and upper percentiles for ticket duration, time categories, tokens per ticket, and cost per ticket. Date, label (any/all), repository, workflow/revision, and production-result filters are part of the REST contract. A token or cost per-ticket observation enters its distribution only when every completed agent run on that ticket has the relevant telemetry; partial totals remain visible with explicit coverage and are never promoted to complete samples.

Workflow completion and production result are deliberately independent. A completed ticket stores `production_result: unassessed | succeeded | failed | rolled_back | not_deployed`, an assessment timestamp, and an optional note. The operator may set this atomically while archiving or revise it later, including while the ticket remains archived. Production success rate is `succeeded / (succeeded + failed + rolled_back)`; unassessed and intentionally not-deployed work stay outside that denominator.

## Deterministic activities

Script nodes reference a repository ID (or `primary`) for repository context and define exactly one activity source: `script_file` or `inline`. File and working-directory references each declare one base and either a static workflow path or a ticket input:

```yaml
repository: primary
script_file:
  relative_to: primary_repository # selected_repository | primary_repository | project_root
  path: tools/deploy.sh            # or path_input: deploy_script
working_directory:
  relative_to: selected_repository
  path: services/api               # or path_input: deploy_directory
```

`script_file` and `working_directory` are resolved independently. A `path_input` must name a non-boolean typed workflow input, so the operator can provide a ticket-specific relative path while selecting the workflow. Every path must be non-empty, portable, relative, and contained beneath its declared base after symbolic links are resolved. Absolute paths, `..` traversal, missing targets, symlink escapes, non-files, and non-executable script files fail before launch. The supervisor process's own current directory never participates in resolution. Legacy `action: verify` definitions normalize when loaded to `.agents/actions/verify.sh` with both references based on the selected repository; newly published workflows use the explicit fields.

Alternatively, the workflow may contain an `inline` object with `language: shell | python | javascript` and a non-empty `code` string. Shell uses `/bin/sh`, Python uses `python3`, and JavaScript uses the supervisor's Node.js runtime. Inline code uses the same configured `working_directory`. It is trusted configuration: it executes with the supervisor process credentials and is not a security sandbox. The editor displays this warning and a human-readable resolution preview.

Immediately before execution, the supervisor observes every ticket repository beneath its project root and builds a context containing repository IDs and absolute paths, the primary and selected repositories, the resolved script path and working directory, current local branches, remote default branches, HEAD SHAs, origin URLs, associated PRs, ticket/workflow/node identifiers, attempt number, and incoming transition context. Git values that cannot be observed are null in JSON and empty in scalar environment variables; the supervisor never guesses branch names. The resolved script path and working directory are also persisted on the durable node run for audit.

All Script forms receive the complete structure in `AGENTIC_CONTEXT_JSON`, repository and PR arrays in `AGENTIC_REPOSITORIES_JSON` and `AGENTIC_PULL_REQUESTS_JSON`, and convenient scalar `AGENTIC_*` variables, including `AGENTIC_SCRIPT_PATH` and `AGENTIC_WORKING_DIRECTORY`. Script files also receive stable `--context-json`, ticket, project-root, selected/primary repository, branch, HEAD-SHA, `--script-path`, and `--working-directory` CLI flags. Inline programs use the equivalent environment contract to avoid language-specific argument semantics. Exit `0` must have an explicit route. Workflows may declare additional exact codes and must provide exactly one default route for every other code, timeout, signal, missing runtime/script, or execution error. Stdout/stderr are never parsed to choose a transition. When `persist_stdout` is enabled, bounded stdout is stored as a separate `.runs` artifact under `TICKETS_ROOT`; the Markdown ticket retains only a short diagnostic tail, byte count, SHA-256 digest, and artifact path. `prompt_tail_lines` independently selects the final zero to 500 stdout lines placed directly in transition context for the next node. Workflow authors own inline-code safety and idempotency; repositories own the implementation and idempotency of script files.

## Metadata and composition

Ticket metadata is a bounded JSON-compatible object stored with the authoritative Markdown frontmatter. Operator endpoints are revision-fenced; agent endpoints are lease-fenced and are included in every assignment callback contract. Keys are literal identifiers rather than path expressions. Read and Write nodes use the same store, which permits deterministic exact-match branches and loops without parsing agent or terminal prose. Metadata is coordination data, not a replacement for repository artifacts or full logs.

A workflow node invokes a child workflow using the child revision pinned when the ticket starts. The runtime retains a call frame, enters the child start node, and returns only when a child terminal node supplies its numeric status code. Parent and child visit/loss accounting is namespaced by workflow revision, so reused node IDs cannot collide. Nesting and the root transition ceiling remain bounded.

Fan-out preserves the prior transition context for every branch, but branch execution is deliberately sequential in V3. Each branch runs to the declared fan-in under the same ticket and supervisor affinity. The fan-in proceeds only after all branches arrive, then makes the combined branch summaries, configured output tails, and artifact links available to its successor. This supplies durable fork/join semantics without introducing parallel leases or conflicting repository writers.

A supervisor advertises its available agent providers and detected activity capabilities (`repository_action`, `inline_shell`, `inline_javascript`, and `inline_python`) with every claim. Before a ticket is first pinned to that supervisor, the tracker checks every enabled agent and Script node and refuses ownership when a required provider or runtime is unavailable. A supervisor also cannot claim the current Script unless it advertises that exact capability. Supervisors poll lease control while Scripts run, heartbeat long executions, terminate the child process on interruption, cancellation, tracker-control failure, or fencing, and never submit a result after an interrupt request.

Operator cancellation and failure requests do not immediately discard an active lease. They create a terminal interruption request, retain repository ownership, and wait for the supervisor to stop Herdr or the Script child and acknowledge the fence. The acknowledgement closes the node run and applies the requested terminal status. An unacknowledged interruption expiry blocks the ticket for human attention instead of pretending the execution stopped safely. Retry clears only the current node's consecutive-loss count and cannot bypass visit or transition ceilings.

## Human gates and editing

A human gate exposes its configured labels and descriptions in the ticket UI. Choosing one records the stable choice ID and follows its target. Choices may require a human comment before the tracker accepts the decision. A running node cannot be graph-edited in place. Operators may edit a draft workflow, publish a new revision, and explicitly migrate a paused ticket to a mapped node.

A human gate may configure `github_watch` with a PR phase and one of that gate's choice IDs as its feedback outcome. While the ticket waits at that gate, the existing GitHub observer persists its per-PR cursors and follows the declared choice only for newly observed human feedback or a newly observed merge conflict. A completed terminal node may instead declare an explicit `feedback_target`; completed-ticket follow-up transitions to exactly that node. GitHub routing is never inferred from an `implementation` prompt or phase. GitHub observation is an event source attached to a durable wait boundary, not an executable workflow node. This supports specification-review, final-PR-review, and custom repair loops without teaching agents or scripts to poll GitHub.

The workflow editor is graph-first: it draws labeled routes and loop-back paths; provides structured editors for inputs, stages, agent outcomes/profiles, Script exit/output controls, human choices, metadata cases/writes, child status routes, and fork/join edges; uses node dropdowns for every target; validates references, reachability, prompt/action contracts, conditions, required/default routes, child references, fork joins, and loop bounds before saving; and keeps raw YAML as a synchronized advanced escape hatch. The prompt and workflow libraries expose separate New and Clone actions. Per-ticket customization clones the pinned workflow into a ticket-specific workflow artifact; it never mutates a shared template.

## Compatibility projection

`current_node`, its resolved provider, and its conversation key are authoritative. Workflow-defined stages and nodes drive the queue, graph, ticket details, sessions, attempts, and runtime display. The fixed `phase`, `status`, phase-agent fields, and legacy provider fields are internal compatibility projections only. New tickets pin the standard V3 workflow. Valid tickets without a pinned workflow remain on disk and accessible through direct APIs but are not displayed in the V3 work queue. Invalid files remain visible so operators can repair them.

## Shipped workflows

The tracker seeds three editable workflow artifacts:

- **Standard delivery** retains optional specification and review stages with specification GitHub feedback observation.
- **Dev Only** specifies, waits for specification approval while observing its PR, implements, independently reviews, waits for human PR approval while observing implementation PRs, invokes an explicitly merge-authorized agent prompt, and runs the primary repository's `.agents/actions/callback.sh` script.
- **End to End** specifies and waits for approval, asks an agent to create and baseline a Postman collection, implements, independently reviews, asks the work agent to deploy and validate non-production, and routes `validated`, `validation_failed`, `deployment_failed`, and the ordinary failure callback through rollback before human recovery or review. It then waits for human code/testing approval while observing implementation PRs and asks the work agent to create a release ticket.

Repository-specific Postman, deployment, rollback, merge, and release mechanics deliberately remain inside full-capability agent nodes. Agents pass durable natural-language results through `summary` and actionable next-step context through `handoff`; ticket and PR state remain available to every node. Bounded ticket metadata is available when deterministic nodes need a small value they cannot safely rediscover. Large or authoritative domain artifacts remain in repositories or external systems.

## Interfaces

V3 retains the lease endpoints and adds:

- workflow list, read, create/update, validate, clone-for-ticket, and ticket migration endpoints;
- generic human-gate decision endpoint;
- deterministic activity claim and result endpoints;
- ticket-operator and lease-fenced worker metadata read/write endpoints;
- node metadata and allowed outcomes in agent claims;
- a lease-fenced assignment refresh endpoint used by the owning supervisor to update the active filesystem bundle;
- `outcome` on agent completion, while retaining the legacy review `decision` form.
- a read-only, filterable metrics endpoint derived from durable ticket history;
- revision-fenced production-assessment and archive-with-assessment operations for completed tickets.

SSE remains best-effort invalidation only. Markdown and artifact files loaded through REST remain authoritative.

## Acceptance criteria

- Prompt and workflow revisions survive later edits and tickets load their pinned revisions.
- The standard V3 workflow reproduces optional specification, approval, implementation, optional independent review, repair loops, and terminal completion.
- A custom workflow can reuse one prompt in multiple agent nodes.
- A script node resolves one executable and one working directory from explicit contained bases (including ticket-provided relative paths), or runs trusted inline shell/Python/JavaScript from that directory; it externalizes full bounded output and follows exact/default exit-code routing without parsing prose.
- Script stdout persistence and prompt-tail injection are independently configurable, and the next prompt receives an artifact URL when persistence is enabled.
- Read and Write nodes route and mutate JSON ticket metadata without evaluating expressions.
- Child workflows pin their revisions, return numeric terminal status codes, and retain isolated visit/loss accounting.
- Fan-out branches receive the same predecessor context; fan-in waits for and combines every declared branch before proceeding.
- Agent-profile aliases pin provider/model/reasoning tuples and later configuration edits do not alter running tickets.
- Human choices and agent outcomes are presented with labels and descriptions and follow only declared targets.
- Workflow routes may declare explicit success/failure/neutral metric classes; unclassified routes remain visible and are excluded from the success-rate denominator.
- Required human comments are enforced.
- Ticket inputs and configurable-stage selections persist in Markdown; required stages cannot be disabled.
- Condition-false and disabled-stage paths are recorded as engine bypasses rather than agent outcomes.
- Agent summary and handoff context are durable and injectable into the next assignment prompt.
- Metrics are grouped by immutable workflow revision, expose telemetry coverage, and never treat unavailable cost or tokens as zero.
- Production assessment remains editable after ticket archival and is not inferred from workflow completion.
- A loop is stopped by node-visit or workflow-transition bounds.
- Concurrent/stale callbacks are lease- and node-run-fenced.
- Herdr idle/done never completes a node without a callback.
- Initial Herdr prompts remain small and point to exact durable filesystem paths; a callback reminder repeats both the absolute `START_HERE.md` and helper paths after compaction.
- Every agent node run has a recoverable bundle, live guidance refreshes its snapshots before delivery, and edits to bundle files never mutate tracker state.
- Work and review conversation keys resume the correct sessions through loops.
- Explicit per-node providers and conversation records remain authoritative even when legacy phase projections differ.
- Reused conversations use per-node telemetry baselines, late final snapshots update only their lease-matched node run, and ticket totals expose incomplete token/cost coverage.
- Script interruption/cancellation fences results and terminates the running child process; node-scoped lease losses do not combine across same-phase nodes.
- Initial supervisor ownership and current Script claims reject missing provider or activity-runtime capabilities.
- Gate-scoped GitHub observation follows only the configured human choice and does not retrigger for feedback already captured by the PR cursor.
- Completed-ticket GitHub observation follows only the terminal node's declared feedback target.
- The Dev Only and End to End defaults validate against the shipped reusable prompts.
- Valid tickets without workflow fields are omitted from the V3 work queue, while invalid files remain visible for repair.

## Explicit exclusions

V3 does not add a database, a sandbox for trusted inline workflow code, a general condition expression language, parallel fan-out leases, merge permission profiles, provider permission profiles, terminal transcript replication, multi-node tracker deployment, or replacement of Herdr's native session model. A merge occurs only when a workflow reaches an agent node whose prompt explicitly authorizes it.
