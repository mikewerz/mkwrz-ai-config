# Agentic Software Factory V3

## Decision

V3 replaces the fixed delivery pipeline with a small, durable workflow engine while preserving the successful agent interaction contract:

> The tracker decides which durable node is active. A full-capability agent decides how to achieve an agent node and explicitly calls back with its outcome.

The tracker is the control plane and source of truth. Supervisors remain generic executors near repositories and Herdr sessions. Herdr lifecycle is observational and never advances a workflow.

For practical workflow YAML, node I/O, and reusable-prompt guidance, see the [Workflow and Prompt Authoring Guide](../workflow-and-prompt-authoring.md).

## Artifacts

Artifacts live beneath `TICKETS_ROOT`:

```text
tracker-config.yaml
prompts/
  <prompt-id>.md
  .versions/<prompt-id>/<sha256>.md
workflows/
  <workflow-id>.yaml
  .versions/<workflow-id>/<sha256>.yaml
.attachments/<ticket-id-digest>/<attachment-id>
<ticket>.md
```

Prompts are independently reusable Markdown artifacts. Workflows reference prompt IDs. Every distinct saved revision is content-addressed, retained, and given a simple per-artifact `v1`, `v2`, and later display number. A tracker-owned release catalog gives every workflow family exactly one default revision and any number of named trial revisions. Publishing a trial does not move the default; promotion atomically moves only the pointer. A ticket records its original workflow assignment, revision, display version, selection source, and assignment time when it is created. Edits, promotion, or restoring a built-in default never silently alter running or completed work. The operator may restore every built-in prompt and workflow to shipped content while preserving custom artifacts and retained revisions.

## Workflow definition

A workflow is a directed graph with one start node and a configurable transition ceiling. Node IDs are stable within a revision. Workflow definitions also declare typed ticket inputs and ordered display stages.

Inputs are Boolean or select values with labels and defaults. Nodes may compare one declared input to one literal value and follow an explicit `otherwise` target when the comparison is false. The engine never evaluates source code or a general expression language.

Stages group nodes for the ticket UI and declare an operational role: specification work, delivery work, independent review, or terminal. This role projects the active workflow node into the coarse `phase` and `status` fields retained for storage and filtering; it does not select a provider, conversation, prompt, PR rule, or GitHub-follow-up route. A stage is either required or ticket-configurable. Configurable stages declare their default and one explicit bypass target. Tickets persist their input values and enabled-stage selections in Markdown. Required stages cannot be disabled through ordinary ticket controls.

Supported node types are:

- `agent`: sends a reusable prompt through the existing supervisor/Herdr handshake. It declares an agent-profile alias, conversation key, and typed outcomes containing an ID, label, description, and target.
- `script`: runs either a configured script file or trusted inline shell, Python, or JavaScript on a supervisor and routes its numeric exit code through declared mappings. Executable resolution and process working directory are separate, explicit settings. It may persist stdout separately and place a configured tail into the next transition context.
- `human_gate`: waits for one of its declared human choices. Each choice contains an ID, label, description, target, and optional required-comment policy.
- `wait`: records a tracker-owned external delay with bounded backoff, deterministic jitter, and an absolute deadline. It holds no lease or supervisor capacity and routes either `elapsed` or `timed_out`.
- `read`: exact-matches one ticket metadata value against declared JSON values and follows an explicit default route.
- `write`: atomically replaces one ticket metadata value and follows its single declared target.
- `workflow`: invokes a pinned child workflow and routes the child's numeric terminal status code when the child returns.
- `fan_out`: copies its incoming transition context into two or more declared branches. V3 executes those branches sequentially under the ticket's single durable lease/ownership model.
- `fan_in`: waits until every branch declared by its fan-out has arrived, combines their summaries, prompt outputs, and output-log references, and follows one target.
- `terminal`: completes, fails, or cancels the top-level ticket, and returns a numeric status code when reached inside a child workflow.

The tracker configuration defines a default agent-profile alias and named aliases, each resolving to a provider, exact model, and reasoning setting. New installations ship `claude` as Claude Opus 4.8 at high reasoning and `codex` as GPT-5.6 Sol at high reasoning; the bundled workflows explicitly use Claude for work nodes and Codex for independent review. Every agent node selects an alias; the resolved tuple is pinned into the ticket with the workflow revision and passed to the provider's native CLI on launch/resume. Changing an alias affects future tickets, not work already pinned. The current node's pinned resolved profile and `conversation_key` are authoritative. Conversation records keyed by that key own Herdr pane/session continuity independently of graph shape, so one workflow revision cannot assign the same conversation key to incompatible profiles.

Every agent node also declares or defaults an explicit conversation policy: resume one generation across visits, start fresh for each new graph visit, or reset after a configured number of visits. Retries of one logical visit and provider-quota pauses retain their generation. The tracker records generation and reset reason; the supervisor includes the generation in Herdr pane identity so an explicit reset cannot restore a stale session.

An agent node may declare `pull_request_requirement` with a PR phase and either `scope: any` or `scope: primary`. The tracker enforces that contract on completion. PR requirements are never inferred from node IDs or prompt names, so nodes may be renamed or reused without weakening completion guarantees.

`skipped` is not a callback outcome. When a condition is false or a configurable stage is disabled, the tracker records an engine-owned `bypassed` node run and follows the declared `otherwise` or stage bypass target. Agents and humans never need to know or submit a magic skip string. Workflows must use the current typed `when`, route, stage, and node schemas. Startup creates missing shipped artifacts and repairs a structurally invalid shipped default from its current built-in definition after archiving the original bytes. Valid workflows, custom workflow IDs, and prompt files are never rewritten automatically.

Every declared route may also carry `metric_class: success | failure | neutral`. This classification is analytics metadata, not control flow: route IDs remain stable workflow contracts and the engine never guesses success from their spelling. Unclassified custom routes remain valid and are reported separately until an operator classifies them. Engine-owned bypasses, interruptions, and lease losses are operational dispositions rather than successes or failures.

## Runtime and fencing

Mutable runtime belongs to the ticket, not the workflow definition. The ticket records:

- pinned workflow ID and revision;
- current node;
- transition count, per-node visit counts, and per-node attempt/loss counters;
- immutable node-run records;
- active lease and node-run ID;
- reusable conversation references keyed by conversation key.
- typed workflow input values, enabled-stage selections, and the transition context entering the current node.
- JSON-compatible ticket metadata, pinned child-workflow revisions, resolved agent profiles, nested-workflow call frames, and in-progress fan-out frames.

Every visit creates a node run containing the workflow revision, node ID/type, visit and attempt numbers, supervisor/provider, timestamps, input snapshot digest, outcome, summary, optional handoff, and reported artifacts. Complete run history is stored in a revision-addressed, integrity-checked ledger beneath `TICKETS_ROOT/.runs`; authoritative ticket YAML retains a bounded ledger reference and no expanding run array, while REST responses hydrate the full history. The operator ticket view consolidates the complete hydrated run ledger, generic artifacts, execution/checkpoint manifests, persisted outputs, checkpoint bundles, and attachments into one evidence browser with open/download controls. Every graph move uses the same transition operation, which replaces incoming context and records its source, target, outcome, summary, handoff, actor, timestamp, visit, and resulting node state. Agent and activity callbacks are fenced by lease and node-run ID. Stale callbacks cannot move the graph.

Lease-loss escalation is scoped to the current node rather than its projected phase. Any accepted agent or Script callback resets that node's consecutive-loss count. The first two unexplained losses return the same node to ready; the third blocks it for operator attention without contaminating other nodes in the same phase.

Loops are ordinary explicit edges. Execution stops for human attention when a node exceeds its `max_visits` or the workflow exceeds `max_transitions`. These are orchestration safety limits, not judgments about agent quality.

## Agent nodes

The existing interaction is retained:

1. A supervisor claims a ready agent node.
2. It writes a supervisor-local durable assignment bundle for that exact node run.
3. It starts or resumes the ticket conversation in Herdr and sends a small bootstrap containing the exact `START_HERE.md`, project-root, and callback-helper paths.
4. The agent works with its normal tools and permissions.
5. The agent may comment, ask one or many questions, complete with a declared outcome plus summary and optional handoff, or fail.
6. The tracker records the node run and follows the matching edge.
7. The next node-run bundle renders the incoming node, outcome, summary, handoff, configured Script-output tail, and link to any full output artifact. It also documents lease-fenced metadata read/write callbacks. Reusable node prompts may reference the same metadata tags.
8. The agent stops. Herdr idle/done without a callback causes at most one callback reminder and never advances the workflow.

At each Agent-run boundary the supervisor best-effort captures two complementary provenance artifacts: bounded, human-readable Herdr scrollback and the native harness session JSONL files that Codex or Claude expose. These bytes are uploaded to tracker-owned immutable storage after a question, callback, interruption, disappearance, or delivery failure and remain linked to the historical node-run lease even after the callback fences further workflow mutation. Metadata states the pane/session/provider, capture disposition, file role, and whether each capture is full, bounded, or partial. Capture and display are observational only; missing evidence cannot alter an outcome or route an edge.

Starting an agent in a newly created pane or restoring one into a saved pane may briefly fail while a macOS login shell initializes. The supervisor retries only Herdr's `agent_pane_busy` startup error at 500-millisecond intervals for at most 10 seconds. Acceptance of `agent start` is not sufficient to send work: the supervisor then waits for Herdr's `interactive_ready=true` and `launch_pending=false` readiness predicate to remain stable for a short settle interval. A Herdr version that omits both fields receives a conservative bounded delay instead. Other errors fail immediately, and exhausting the busy or readiness window returns an operational delivery failure without advancing or failing the workflow semantically.

Herdr may report `agent_prompt_stalled` or a wait timeout even when Claude is processing the bootstrap or when its text is visible but unsent in the composer. The supervisor never responds by pasting the full bootstrap again on the same lease. It polls lifecycle and unwrapped pane content, treats only a semantic transition from settled `idle`/`done` to `working` as activity-based delivery proof, and sends only `Enter` when it sees either the unique durable assignment path or Claude's collapsed `[Pasted text #N +M lines]` composer token. Pane repaint revisions, late native-session discovery, and unknown/blocked startup transitions are not delivery proof. Exhausting the bounded recovery window clears any possibly staged composer with `Ctrl+C`, then produces an operational `delivery_failed` run and no workflow transition.

The bundle lives beneath the supervisor's configurable `ASSIGNMENT_ROOT` as `<supervisor-id>/tickets/<ticket-id>/runs/<attempt>-<node-id>-<node-run-id>/`. It contains `START_HERE.md`, `ticket.md`, `node.md`, `incoming.md`, `attachments.md`, `context.json`, `callbacks.md`, `callbacks.json`, an executable `callback` helper, verified local attachment copies under `attachments/`, `updates/`, and `outbox/`. A ticket-level `ACTIVE.json` points to the current run. IDs are used directly in assignment directory names rather than normalized. A quota pause retains the same run; a retry or later loop visit creates a new run directory.

The tracker, not an individual supervisor, owns uploaded content so that retries and assignments on other VMs see the same files. Binary content is stored outside Markdown beneath `TICKETS_ROOT/.attachments`; frontmatter keeps bounded metadata and the SHA-256 digest. Upload and removal are revision-fenced ticket mutations. A live mutation queues guidance so the owning supervisor refreshes the assignment manifest and materializes newly added files before prompting the agent. The operator UI supports multi-file selection, image previews, downloads, and removal. Each file is limited to 25 MB.

The files are recovery snapshots, not a second control plane. Agents are told that edits may be useful as scratch notes but are not observed by the supervisor and never mutate the authoritative ticket, workflow, or callback contract. No permission profile, read-only mount, watcher, or sanitizing filename layer is introduced. Tracker callbacks and APIs remain authoritative.

The generated callback helper owns the concrete schemas and lease URLs for comment, batched questions with answer options, completion, failure, and metadata reads/writes. It validates the selected completion outcome, sends the request, and records a local request/response pair. `START_HERE.md` tells the agent where to read the full contract and how to print a schema example. This is a plain generated executable, not a skill.

The default assignment prompt is intentionally only a bootstrap. The durable files separate incoming transition context, the current-node contract, and the callback protocol. Reusable prompts tell agents to choose an exact declared outcome ID, use `summary` as the node's durable record, and use `handoff` only for actionable context needed by the next node. Reusable prompts cover specification, implementation, review, Postman baseline design, non-production validation, rollback, merge, and release-ticket creation while leaving execution strategy to the full-capability agent.

Live guidance, question answers, and live-ticket edits refresh the current ticket and node snapshots first, then create an ordered Markdown file beneath `updates/`. The follow-up Herdr message contains the exact update, `START_HERE.md`, and callback-helper paths. If Herdr becomes idle or done without a terminal callback, the single reminder repeats the exact absolute `START_HERE.md` and helper paths; it never assumes the initial message survived compaction.

The durable node instructions deny merging by default unless the current node prompt explicitly authorizes it. The reusable `merge.md` prompt is that authority in the shipped Dev Only workflow: it requires a still-applicable preceding human approval, passing protections, mergeability, and no newer invalidating feedback. There is no separate merge-permission field in workflow YAML or the UI.

Review remains an independent conversation and role, not a restricted sandbox. Workflow authors select a separate conversation key and may use an opposite-provider profile alias when independent-provider review is required.

## Harness telemetry and ticket cost

Usage observation uses a versioned provider-neutral snapshot rather than adding provider fields to the ticket schema. Each snapshot identifies its harness and native session, exact observed model IDs, reasoning setting plus provenance, normalized input/cache-write/cache-read/output/reasoning token counts, cost value plus `reported | estimated | unavailable` provenance, context use, rate-limit windows, and scalar harness attributes. Built-in Claude and Codex adapters are registered behind the same interface; future harnesses add an adapter without changing tracker storage or UI contracts.

Every agent node records a baseline snapshot and latest snapshot. The tracker, not the supervisor or provider adapter, derives non-negative node deltas. A new native conversation starts from an explicitly marked zero baseline; when cost is initially unavailable, that zero remains schema-valid and a later known cumulative cost is attributed to the fresh run. A reused conversation starts from its cumulative usage when that node begins. This makes durable node runs independently aggregable without double-counting earlier nodes in the same conversation. Liveness heartbeats are independent from telemetry validation, and the supervisor submits accounting through `POST /api/work/{lease}/telemetry`; telemetry rejection is logged but cannot interrupt assignment delivery or lease renewal. Because an agent may call `complete` immediately before its final session record is flushed, the telemetry endpoint may update the retained node run by lease ID after the execution lease has closed, but can never transition the workflow.

Each node run also owns a provider-neutral timing ledger. Heartbeats accrue active runtime, human gates accrue human-wait time from node entry through the decision, and an exhausted harness rate-limit window with a future reset accrues quota-paused time while the supervisor continues heartbeating the lease. If a five-hour Claude or Codex limit expires between heartbeats, accounting splits the interval at the declared reset timestamp and resumes active time automatically. Wall time remains separately derivable from the run timestamps. Ticket token, cost, active-time, quota-pause, human-wait, and elapsed totals are derived from durable node runs so repair loops and repeated visits are included without storing a second rollup that can drift.

The dashboard displays live and per-node metrics and computes ticket totals from node deltas. Ticket runtime, graph, run-history, total, and execution-recap views display uncached-input, cached-input, cache-write, output, and reasoning-output counts separately; a combined provider total may remain supplemental but is never the only ticket-level token figure. Coverage denominators include only actual agent executions, excluding bypassed nodes and assignment delivery failures. Harness-reported cost is shown as reported and is never replaced. When cost is unavailable but normalized token usage and an exact harness/model pricing entry exist, the tracker computes an estimated cost from separately configured uncached-input, cache-read, cache-write, and output rates. The estimate retains the pricing ID, HTTPS source, and effective timestamp. Missing subscription cost and unmatched models remain unavailable rather than being treated as zero. Telemetry collection is best effort and cannot block, fail, or complete agent work.

The Configuration page may additionally estimate a Claude or Codex subscription's weekly observed-workload equivalent when its harness supplies a seven-day rate-limit percentage and reset identity. The tracker compares rate-limit movement only within one reset window and scales the matching completed durable-node token and known/estimated API-cost deltas to 100 percent. It reports the median, sample coverage, observed percentage points, and confidence rather than presenting the result as a contractual quota. Multiple supervisors may be assigned one provider-scoped quota-account alias when they use the same subscription; Claude and Codex accounts on one supervisor are always kept separate. API-key billing, Claude installations without the optional status-line feed, and any plan that omits a weekly window remain explicitly unavailable. This derived view is read-only accounting: it cannot affect claims, routing, pauses, or workflow transitions.

## Factory metrics and production assessment

Workflow metrics use ticket assignment rather than the mutable library head. Node and efficiency distributions include every completed ticket assigned to the revision, with revision-crossover tickets reported and excluded from clean efficiency comparisons. Effectiveness retains the wider settled cohort so failed and cancelled tickets remain in completion-rate denominators; blocked and in-progress work is reported separately. Operators can directly compare any two workflow/revision pairs under the same date, label, repository, and production filters. The comparison reports cohort size, completion and production success, cost and token coverage, five-number efficiency summaries, deltas, and side-by-side node reliability. Archived tickets remain part of their historical cohorts.

The tracker derives analytics from authoritative Markdown and immutable node-run history without adding a database in V3. Reports group workflows by both ID and pinned content revision so an edited workflow never blends structurally different nodes into one success rate. Node reports include classified success/failure/neutral/unclassified outcomes, branch frequency, wall/active/human-wait/quota-pause time, interruptions, bypasses, lease losses, token/cost totals, and coverage. Agent comparisons use the ticket-pinned profile alias plus resolved provider, model, and reasoning tuple.

Platform reports include ticket, token, known-cost, active-time, quota-pause, and human-wait totals plus five-number summaries and upper percentiles for ticket duration, time categories, tokens per ticket, and cost per ticket. Tickets may optionally store `estimated_human_days`. Configuration supplies a non-negative USD day rate; reports show human-day and human-cost distributions plus a human-versus-factory comparison. The comparison includes only completed tickets with an estimate and complete cost coverage, and clearly treats human effort as a planning estimate rather than measured labor. Date, label (any/all), repository, workflow/revision, and production-result filters are part of the REST contract. A token or cost per-ticket observation enters its distribution only when every completed agent run on that ticket has the relevant telemetry; partial totals remain visible with explicit coverage and are never promoted to complete samples.

Workflow completion and production result are deliberately independent. A completed ticket stores `production_result: unassessed | succeeded | failed | rolled_back | not_deployed`, an assessment timestamp, and an optional note. The operator may set this atomically while archiving or revise it later, including while the ticket remains archived. Production success rate is `succeeded / (succeeded + failed + rolled_back)`; unassessed and intentionally not-deployed work stay outside that denominator.

## Deterministic activities

Script nodes reference a repository ID (or `primary`) for repository context and define exactly one activity source: `script_file` or `inline`. File and working-directory references each declare one base and either a static workflow path or a ticket input:

```yaml
repository: primary
script_file:
  relative_to: primary_repository # selected_repository | primary_repository | project_root
  path: tools/deploy.sh            # or path_input: deploy_script
working_directory:
  relative_to: selected_repository
  path: services/api               # or path_input: deploy_directory
```

`script_file` and `working_directory` are resolved independently. A `path_input` must name a non-boolean typed workflow input, so the operator can provide a ticket-specific relative path while selecting the workflow. Every path must be non-empty, portable, relative, and contained beneath its declared base after symbolic links are resolved. Absolute paths, `..` traversal, missing targets, symlink escapes, non-files, and non-executable script files fail before launch. The supervisor process's own current directory never participates in resolution. Workflows must declare these references explicitly; there is no implicit action-to-script mapping.

Alternatively, the workflow may contain an `inline` object with `language: shell | python | javascript` and a non-empty `code` string. Shell uses `/bin/sh`, Python uses `python3`, and JavaScript uses the supervisor's Node.js runtime. Inline code uses the same configured `working_directory`. It is trusted configuration: it executes with the supervisor process credentials and is not a security sandbox. The editor displays this warning and a human-readable resolution preview.

Immediately before execution, the supervisor observes every ticket repository beneath its project root and builds a context containing repository IDs and absolute paths, the primary and selected repositories, the resolved script path and working directory, current local branches, remote default branches, HEAD SHAs, origin URLs, associated PRs, ticket/workflow/node identifiers, attempt number, and incoming transition context. Git values that cannot be observed are null in JSON and empty in scalar environment variables; the supervisor never guesses branch names. The resolved script path and working directory are also persisted on the durable node run for audit.

All Script forms receive the complete structure in `AGENTIC_CONTEXT_JSON`, repository and PR arrays in `AGENTIC_REPOSITORIES_JSON` and `AGENTIC_PULL_REQUESTS_JSON`, and convenient scalar `AGENTIC_*` variables, including `AGENTIC_SCRIPT_PATH` and `AGENTIC_WORKING_DIRECTORY`. Script files also receive stable `--context-json`, ticket, project-root, selected/primary repository, branch, HEAD-SHA, `--script-path`, and `--working-directory` CLI flags. Inline programs use the equivalent environment contract to avoid language-specific argument semantics. Exit `0` must have an explicit route. Workflows may declare additional exact codes and must provide exactly one default route for every other code, timeout, signal, missing runtime/script, or execution error. Stdout/stderr are never parsed to choose a transition. When `persist_stdout` is enabled, bounded stdout is stored as a separate `.runs` artifact under `TICKETS_ROOT`; the Markdown ticket retains only a short diagnostic tail, byte count, SHA-256 digest, and artifact path. `prompt_tail_lines` independently selects the final zero to 500 stdout lines placed directly in transition context for the next node. Workflow authors own inline-code safety and idempotency; repositories own the implementation and idempotency of script files.

Scripts may write one bounded structured result to `AGENTIC_RESULT_PATH`, containing `metadata` and/or `external_references`. The supervisor validates it; the tracker applies metadata atomically with the fenced activity callback and records both forms on the node run. Exit codes remain the only Script routing signal.

Declared Script artifacts may opt into `agentic-quality/v1` interpretation. The tracker validates the uploaded YAML, stores the raw report immutably, and snapshots a compact normalized attribute index into artifact metadata. A configurable quality registry defines stable keys, labels, scalar types, units, direction, and optional numeric bounds. Unregistered attributes remain ticket evidence but are excluded from cross-ticket aggregates. Quality values never implicitly route the graph; Scripts continue to select declared exit-code outcomes or explicitly persist metadata for a later Read node.

The tracker also owns a generic content-addressed artifact store beneath `TICKETS_ROOT/.artifacts`. Attachments, declared Script output files, checkpoint bundles, checkpoint manifests, per-execution provenance manifests, and Herdr operational-trace chunks use the same immutable byte store and durable metadata records. Configurable total/per-ticket quotas fail before a write exceeds policy. A read-only diagnostic command reports missing, corrupt, invalid, and orphan records/blobs. Automatic maintenance waits out a configurable crash-grace period, reattaches valid orphan records when ownership can be proven, and garbage-collects only unreferenced records and blobs after both grace and retention have elapsed; it never silently deletes referenced evidence. The Markdown ticket retains bounded artifact references and checkpoint summaries, not binary bytes. Assignment bundles expose artifact URLs and digests but do not become authoritative storage. Each node run snapshots its incoming transition, workflow inputs, stage selections, attachments, prior artifact references, prompt revision, and resolved profile when execution begins. Execution manifests use that immutable snapshot alongside timing, telemetry, outputs, repository before/after identity, and supervisor runtime, so a later workflow transition cannot rewrite the run's provenance.

Every Agent-node attempt streams a UUID-scoped, contiguous operational trace to `POST /api/work/{lease}/trace/events`. Exact batch retries are idempotent; sequence gaps and conflicting replays fail closed. Final batches remain acceptable after the terminal callback while that lease is retained on its durable node run. The JSONL trace records normalized Herdr commands, durations and errors, meaningful pane observations, delivery evaluations, recovery actions, and final disposition. It excludes full prompt and terminal bodies in favor of paths, byte counts, and SHA-256 identities. The ticket UI groups immutable chunks into one filterable **Operational traces** timeline per attempt with raw downloads. Trace recording is observational and best effort; it cannot advance, fail, or reroute a workflow.

Tracker and supervisor services emit newline-delimited structured JSON logs. Work lifecycle events include available ticket, workflow node, lease, provider, and supervisor correlation fields. HTTP failures expose stable machine-readable error codes for lease fencing and artifact validation, ownership, integrity, lookup, and quota failures.

Checkpoint nodes capture only the repositories declared on the ticket. The supervisor uses temporary Git indexes to create synthetic commits containing the current working trees without moving normal branches, writes portable Git bundles, uploads them through the active lease, and then reports the manifest. Restore Checkpoint nodes resolve a declared checkpoint source, create a pre-restore checkpoint, restore every declared repository to its synthetic commit, and attempt compensation if any repository fails. Both types use explicit success/default exit-code routes, supervisor capability matching, normal heartbeats, interruption, fencing, node-run accounting, and the centralized transition operation. They do not invoke Herdr. Operator create/restore actions route through configured workflow nodes; active work must acknowledge interruption before either action begins.

## Metadata and composition

Ticket metadata is a bounded JSON-compatible object stored with the authoritative Markdown frontmatter. Operator endpoints are revision-fenced; agent endpoints are lease-fenced and are included in every assignment callback contract. Keys are literal identifiers rather than path expressions. Read and Write nodes use the same store, which permits deterministic exact-match branches and loops without parsing agent or terminal prose. Metadata is coordination data, not a replacement for repository artifacts or full logs.

A workflow node invokes a child workflow using the child revision pinned when the ticket starts. The runtime retains a call frame, enters the child start node, and returns only when a child terminal node supplies its numeric status code. Parent and child visit/loss accounting is namespaced by workflow revision, so reused node IDs cannot collide. Nesting and the root transition ceiling remain bounded.

Fan-out preserves the prior transition context for every branch, but branch execution is deliberately sequential in V3. Each branch runs to the declared fan-in under the same ticket and supervisor affinity. The fan-in proceeds only after all branches arrive, then makes the combined branch summaries, configured output tails, and artifact links available to its successor. This supplies durable fork/join semantics without introducing parallel leases or conflicting repository writers.

A supervisor advertises its available agent providers and detected activity capabilities (`repository_action`, `inline_shell`, `inline_javascript`, `inline_python`, `git_checkpoint`, and `git_restore`) with every claim. Before a ticket is first pinned to that supervisor, the tracker checks every enabled agent and deterministic node and refuses ownership when a required provider or runtime is unavailable. A supervisor also cannot claim the current activity unless it advertises that exact capability. Supervisors poll lease control while deterministic activities run, heartbeat long executions, terminate the child process on interruption, cancellation, tracker-control failure, or fencing, and never submit a result after an interrupt request.

Operator cancellation and failure requests do not immediately discard an active lease. They create a terminal interruption request, retain repository ownership, and wait for the supervisor to stop Herdr or the Script child and acknowledge the fence. The acknowledgement closes the node run and applies the requested terminal status. An unacknowledged interruption expiry blocks the ticket for human attention instead of pretending the execution stopped safely. Retry clears only the current node's consecutive-loss count and cannot bypass visit or transition ceilings.

## Human gates and editing

A human gate exposes its configured labels and descriptions in the ticket UI. Choosing one records the stable choice ID and follows its target. Every choice accepts an optional human comment, and choices may require one before the tracker accepts the decision. The choice ID alone controls routing; the comment is retained as transition context for the destination. A running node cannot be graph-edited in place. Operators may edit a draft workflow, publish a new revision, and explicitly migrate a paused ticket to a mapped node.

A human gate may configure `github_watch` with a PR phase and one of that gate's choice IDs as its feedback outcome. While the ticket waits at that gate, the existing GitHub observer persists its per-PR cursors and follows the declared choice only for newly observed human feedback or a newly observed merge conflict. A completed terminal node may instead declare an explicit `feedback_target`; completed-ticket follow-up transitions to exactly that node. GitHub routing is never inferred from an `implementation` prompt or phase. GitHub observation is an event source attached to a durable wait boundary, not an executable workflow node. This supports specification-review, final-PR-review, and custom repair loops without teaching agents or scripts to poll GitHub.

The workflow editor is graph-first: it draws labeled routes and loop-back paths; provides structured editors for inputs, stages, agent outcomes/profiles, Script exit/output controls, human choices, metadata cases/writes, child status routes, and fork/join edges; uses node dropdowns for every target; validates references, reachability, prompt/action contracts, conditions, required/default routes, child references, fork joins, and loop bounds before saving; and keeps raw YAML as a synchronized advanced escape hatch. The prompt and workflow libraries expose separate New and Clone actions. Per-ticket customization clones the pinned workflow into a ticket-specific workflow artifact; it never mutates a shared template.

The operator shell starts with a unified attention inbox. Ticket summaries project unanswered questions, current Human Gates, blocked/failed nodes, assignment delivery failures, new GitHub feedback, repository claim conflicts, and external waits near wake or deadline without making that projection authoritative workflow state. Each item exposes only its applicable inline action. Ticket workflow views provide a plain-language next-action chain above the graph and retain browser-local selected-ticket, queue-filter, graph-zoom, evidence-tab, and expanded-artifact position. The evidence browser defaults to featured/readable artifacts, can select the newest artifact from each node, filters by node/category/media type, and supports fullscreen previous/next review; manifests and checkpoint bundles are grouped as technical evidence. Completed tickets derive a compact execution recap from the hydrated node-run ledger, pull-request associations, artifact records, accounting telemetry, interventions, and the retroactively editable production result.

## Operational projections

`current_node`, its resolved agent profile, and its conversation key are authoritative. Workflow-defined stages and nodes drive the queue, graph, ticket details, sessions, attempts, and runtime display. `phase` and `status` remain operational projections used for broad state validation and indexing; they do not select agents. Every newly created ticket pins a workflow revision. Files without a pinned workflow remain accessible by direct ID for manual recovery, but are omitted from the work queue and cannot be claimed. Invalid files remain visible so operators can repair them.

## Shipped workflows

The tracker seeds three editable workflow artifacts:

- **Standard delivery** retains optional specification and review stages with specification GitHub feedback observation.
- **Dev Only** specifies, waits for specification approval while observing its PR, implements, independently reviews, waits for human PR approval while observing implementation PRs, invokes an explicitly merge-authorized agent prompt, and runs the primary repository's `.agents/actions/callback.sh` script.
- **End to End** specifies and waits for approval, asks an agent to create and baseline a Postman collection, implements, independently reviews, asks the work agent to deploy and validate non-production, and routes `validated`, `validation_failed`, `deployment_failed`, and the ordinary failure callback through rollback before human recovery or review. It then waits for human code/testing approval while observing implementation PRs and asks the work agent to create a release ticket.

Repository-specific Postman, deployment, rollback, merge, and release mechanics deliberately remain inside full-capability agent nodes. Agents pass durable natural-language results through `summary` and actionable next-step context through `handoff`; ticket and PR state remain available to every node. Bounded ticket metadata is available when deterministic nodes need a small value they cannot safely rediscover. Large or authoritative domain artifacts remain in repositories or external systems.

## Continuous intake and campaigns

Continuous discovery is a control-plane layer above workflow tickets, not an infinite workflow node. A campaign is a durable objective and aggregate capacity boundary. A source is a versioned discovery definition belonging to one campaign. Script sources run periodically on a supervisor; external sources accept pushed observations. Both produce the same bounded candidate schema. A candidate has a stable `external_key`, title, complete ticket description, and optional repository, label, priority, workflow, input, stage, readiness, and metadata overrides.

The tracker is the only admission controller. It serializes candidate decisions, deduplicates on source ID plus external key, enforces source and campaign limits for new tickets per run/day and open, working, or observed-unarchived tickets, allocates IDs, pins a workflow revision and prompt/profile artifacts, writes intake provenance into reserved ticket metadata, and optionally marks the new ticket ready. A capacity denial records `deferred` and is reconsidered by later scheduling passes; repeated facts record `duplicate`; malformed candidates record `rejected`. Admitted tickets remain normal authoritative Markdown tickets with independent run, cost, duration, quality, production, and workflow-release metrics.

Campaigns live as current versioned YAML beneath `TICKETS_ROOT/campaigns`; sources live beneath `TICKETS_ROOT/sources`. Immutable prior content is retained in each library's `.versions` directory. Source runs, candidate decisions, output logs, and source cursors live beneath `TICKETS_ROOT/.intake` and never inflate ticket frontmatter. A run pins the source revision and cursor it started with, owns a separate fenced supervisor lease, and records attempts, supervisor, output digest/size, candidate counts, decisions, failure, and timestamps. Lease expiry requeues the same run. Only a successful completion advances its cursor.

A supervisor Script source resolves `script_path` and `working_directory` relative to that supervisor's configured project root and runs shell, Python, or JavaScript without Herdr. It receives `AGENTIC_INTAKE_*` environment variables and must write `{ "candidates": [...], "cursor": <optional JSON> }` to `AGENTIC_INTAKE_RESULT_PATH`. It may print a bounded diagnostic log. Source execution has its own loop and does not consume agent-provider slots or appear as a ticket node. An enabled source schedules only when its campaign is enabled and no run for that source is ready or running.

Operators author ordinary definitions through structured Campaign and Source forms backed by the same versioned YAML. The advanced YAML editor remains available for uncommon fields. A manually requested preview is a separately identified source run that may execute while its source or campaign is disabled. It validates and displays a bounded candidate summary and persists diagnostics, but does not create candidate-ledger records, admit tickets, count toward admission-run reliability, or advance the durable source cursor. Preview does not sandbox the source process or undo its external effects; source integrations are expected to perform read-only discovery.

An active ticket agent may submit child candidates using its generated callback helper, and an outside operator/agent may submit candidates relative to a parent ticket. This records `intake.parent_ticket_id` but does not bypass admission or imply that every candidate became a ticket. Source/campaign metrics include source reliability, observations, admission/deferral/duplicate/rejection counts, open/working/completed tickets, and recorded production successes.

## Interfaces

V3 retains the lease endpoints and adds:

- workflow list, read, create/update, validate, clone-for-ticket, and ticket migration endpoints;
- generic human-gate decision endpoint;
- deterministic activity claim and result endpoints;
- ticket-operator and lease-fenced worker metadata read/write endpoints;
- node metadata and allowed outcomes in agent claims;
- a lease-fenced assignment refresh endpoint used by the owning supervisor to update the active filesystem bundle;
- `outcome` on every agent completion.
- a read-only, filterable metrics endpoint derived from durable ticket history;
- revision-fenced production-assessment and archive-with-assessment operations for completed tickets.
- campaign/source library, intake overview, manual source trigger, candidate submission, and source-run output endpoints;
- separately fenced source-run claim, heartbeat, completion, and failure endpoints for supervisors;
- parent-ticket and lease-scoped candidate emission endpoints that apply the same admission controller.

SSE remains best-effort invalidation only. Markdown and artifact files loaded through REST remain authoritative.

The tracker builds an in-memory index from every ticket Markdown file before becoming ready. Normal reads, claims, lease sweeps, and metrics use that index; successful tracker writes update it only after atomic Markdown replacement, and filesystem watcher events rebuild it after direct edits. The index is disposable acceleration, never an independent persistence layer. `/api/healthz` reports process liveness, while `/api/readyz` verifies the ticket root, configuration, prompt/workflow libraries, and index. `/api/operations` also reports degraded artifacts, disk availability, index generation, and the latest GitHub-observation and artifact-maintenance outcomes for the operator dashboard.

All outbound HTTP paths use bounded deadlines appropriate to ordinary control calls, long-poll claims, and artifact transfers. Both services emit level-filtered newline-delimited JSON and support bounded rotating files when configured; routine heartbeats are debug-level while failures preserve stable correlation fields.

## Acceptance criteria

- Prompt and workflow revisions survive later edits and tickets load their pinned revisions.
- The standard V3 workflow reproduces optional specification, approval, implementation, optional independent review, repair loops, and terminal completion.
- A custom workflow can reuse one prompt in multiple agent nodes.
- A script node resolves one executable and one working directory from explicit contained bases (including ticket-provided relative paths), or runs trusted inline shell/Python/JavaScript from that directory; it externalizes full bounded output and follows exact/default exit-code routing without parsing prose.
- Script stdout persistence and prompt-tail injection are independently configurable, and the next prompt receives an artifact URL when persistence is enabled.
- Read and Write nodes route and mutate JSON ticket metadata without evaluating expressions.
- Child workflows pin their revisions, return numeric terminal status codes, and retain isolated visit/loss accounting.
- Fan-out branches receive the same predecessor context; fan-in waits for and combines every declared branch before proceeding.
- Agent-profile aliases pin provider/model/reasoning tuples and later configuration edits do not alter running tickets.
- Human choices and agent outcomes are presented with labels and descriptions and follow only declared targets.
- Workflow routes may declare explicit success/failure/neutral metric classes; unclassified routes remain visible and are excluded from the success-rate denominator.
- Required human comments are enforced.
- Ticket inputs and configurable-stage selections persist in Markdown; required stages cannot be disabled.
- Condition-false and disabled-stage paths are recorded as engine bypasses rather than agent outcomes.
- Agent summary and handoff context are durable and injectable into the next assignment prompt.
- Metrics are grouped by immutable workflow revision, expose telemetry coverage, and never treat unavailable cost or tokens as zero.
- Ticket and workflow metrics expose the latest registered quality value per completed ticket, node, and attribute while retaining every immutable per-run YAML report for audit.
- Production assessment remains editable after ticket archival and is not inferred from workflow completion.
- A loop is stopped by node-visit or workflow-transition bounds.
- Concurrent/stale callbacks are lease- and node-run-fenced.
- Restart reconstructs the complete ticket index from Markdown, direct file edits are reconciled through the watcher, and no ticket authority exists only in memory.
- Readiness distinguishes process liveness from required-store/library failures and exposes degraded but schedulable invalid artifacts.
- Stalled tracker, Jira, and GitHub requests terminate at configured deadlines rather than occupying a worker indefinitely.
- Herdr idle/done never completes a node without a callback.
- Initial Herdr prompts remain small and point to exact durable filesystem paths; a callback reminder repeats both the absolute `START_HERE.md` and helper paths after compaction.
- Every agent node run has a recoverable bundle, live guidance refreshes its snapshots before delivery, and edits to bundle files never mutate tracker state.
- Work and review conversation keys resume the correct sessions through loops.
- Pinned per-node profiles and conversation records remain authoritative throughout loops and retries.
- Reused conversations use per-node telemetry baselines, late final snapshots update only their lease-matched node run, and ticket totals expose incomplete token/cost coverage.
- Script interruption/cancellation fences results and terminates the running child process; node-scoped lease losses do not combine across same-phase nodes.
- Initial supervisor ownership and current Script claims reject missing provider or activity-runtime capabilities.
- Gate-scoped GitHub observation follows only the configured human choice and does not retrigger for feedback already captured by the PR cursor.
- Completed-ticket GitHub observation follows only the terminal node's declared feedback target.
- The Dev Only and End to End defaults validate against the shipped reusable prompts.
- Valid tickets without workflow fields are omitted from the V3 work queue, while invalid files remain visible for repair.
- Scheduled discovery pins its source revision and cursor, requeues expired source leases, and advances the cursor only after a successful result.
- Repeated source/external-key observations never create duplicate tickets; source and campaign run/day/open/working/unarchived limits produce durable deferred decisions.
- Every admitted candidate becomes an ordinary workflow-pinned Markdown ticket whose metrics remain independent from the source run and campaign rollup.

## Explicit exclusions

V3 does not add a database, a sandbox for trusted inline workflow code, a general condition expression language, parallel fan-out leases, merge permission profiles, provider permission profiles, terminal transcript replication, multi-node tracker deployment, or replacement of Herdr's native session model. A merge occurs only when a workflow reaches an agent node whose prompt explicitly authorizes it.
