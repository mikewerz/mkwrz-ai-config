# Agentic Project Tracker

The tracker is the durable control plane for the lightweight AI Self-Coordinator. It stores every ticket as authoritative Markdown, exposes claims and small agent callbacks over REST, and gives an operator a React dashboard for ticket authoring, workflow visibility, agent monitoring, approvals, feedback, guidance, and recovery.

It coordinates work boundaries. It does not prescribe how an assigned agent plans, edits code, runs tests, uses Git, or creates pull requests.

The preserved lightweight baseline is [`docs/specs/init.md`](docs/specs/init.md). The implemented V3 software-factory contract is [`docs/specs/v3.md`](docs/specs/v3.md). For a practical, agent-oriented guide to designing graphs and reusable prompts, see [`docs/workflow-and-prompt-authoring.md`](docs/workflow-and-prompt-authoring.md).

For the clean, history-free import into the consolidated `mkwrz-ai-config/workflow` layout, including exclusions and post-copy verification, see [`docs/migration/mkwrz-ai-config.md`](docs/migration/mkwrz-ai-config.md).

## Run locally

Node 22.12 or newer is required.

For normal VM operation, configure `.env` and run the production launcher:

```bash
cp .env.example .env
./run.sh
```

`run.sh` changes to the repository directory, runs `npm ci` when dependencies are absent or older than `package-lock.json`, builds the server and React production bundle, and replaces itself with the compiled server process. The UI and REST API are both served from `HOST:PORT`; there is no Vite port in this mode.

For source-watching development instead:

```bash
npm ci
npm run dev
```

Set `TICKETS_ROOT` to the directory containing the authoritative ticket Markdown files. The API defaults to `http://127.0.0.1:4310`; Vite serves the development UI separately and proxies `/api` requests to it.

Continuous intake is a tracker-owned layer above tickets and workflows. Versioned campaign YAML lives in `TICKETS_ROOT/campaigns`, versioned source YAML in `TICKETS_ROOT/sources`, and source-run/candidate/cursor records in `TICKETS_ROOT/.intake`. A scheduled supervisor Script discovers standardized candidates; the tracker alone applies stable source/key deduplication, per-run and per-day admission limits, open/working/unarchived capacity limits, local ID allocation, workflow pinning, and parent-ticket provenance. Every admitted candidate is an ordinary Markdown ticket with independent workflow metrics. Discovery runs are measured separately, so a long-lived improvement campaign never becomes one unbounded ticket run.

The tracker also creates `tracker-config.yaml`, `prompts/`, `workflows/`, and a private content-addressed `.artifacts/` store beneath `TICKETS_ROOT`. Ticket attachments are revision-fenced, integrity-checked files of up to 25 MB each; their name, media type, byte count, digest, and creation time remain visible in Markdown frontmatter while binary content stays outside the ticket. The same tracker-owned store holds declared Script artifacts and portable checkpoint bundles/manifests; supervisors only stage or materialize those bytes while executing a lease. Configurable store-wide and per-ticket quotas are enforced before writes. Automatic maintenance recovers valid crash-orphaned records after a grace window and removes only unreferenced records/blobs after both grace and retention have elapsed; referenced ticket evidence is never silently expired. `npm run artifacts:diagnose -- /path/to/tickets` performs the same integrity/orphan scan without deleting anything. Its Configuration page manages these policies alongside the repository catalog, the `AGENT-nnnn` ticket sequence, reusable agent-profile aliases, editable token pricing, the human-day comparison rate, optional Jira Cloud settings, and optional GitHub PR observation. It also shows empirical Claude and Codex weekly-allowance estimates when their harnesses report a seven-day percentage window: completed node token/cost deltas are divided by their observed percentage-point change, with sample count and confidence kept visible. Supervisors using one subscription account can be mapped to a provider-scoped shared quota-account alias. API-key billing, Claude installations without the optional status-line feed, and plans without a reported weekly window remain explicitly `not reported`; the tracker never invents a cap. New installs include `claude` (`Claude Opus`, `claude-opus-4-8`, `high`) and `codex` (`Codex Sol`, `gpt-5.6-sol`, `high`) aliases. The shipped workflows use Claude for specification/implementation and Codex for independent review. An alias pins its provider/model/reasoning tuple into each ticket when its workflow starts, so changing it affects new work without silently changing running work. Updates are revision-fenced and atomically replace the YAML file while preserving future top-level settings that the current UI does not know about.

The Prompt Editor manages reusable Markdown artifacts in `TICKETS_ROOT/prompts`. It can create or clone prompts, shows the workflow nodes that reference each prompt, documents `{{meta_tags}}`, and renders a dummy-ticket preview. The Workflow Editor manages validated YAML graphs in `TICKETS_ROOT/workflows`, shows their nodes and edges, and publishes content-addressed revisions. Each workflow family has one active default revision and may have any number of trial revisions. Publishing a trial does not change new-ticket routing; promoting a revision retires the previous active default, changes only the default pointer, and never changes an existing ticket. Retired history is hidden in the editor until requested. Release labels and state live in `TICKETS_ROOT/workflows/.releases.yaml`, while immutable definitions remain under `.versions/`. The simple `v1`, `v2`, and later numbers identify unique content, not activation chronology, so restoring shipped content may legitimately reactivate an earlier version. Content hashes remain the ticket-pinned identity. A numbered revision can be exported as a portable JSON bundle containing its exact YAML plus the current exact revisions of all referenced prompts. Import verifies every digest and dependency, preserves previous prompt history, makes a new workflow family active, and installs a collision with an existing family as a trial rather than replacing its default. Agent-profile definitions, child workflows, credentials, tickets, and artifacts are not copied. Configuration can restore all shipped prompts and workflows without rewriting a ticket's pinned artifacts.

The assignment prompt is deliberately a small bootstrap that points to the supervisor-local `START_HERE.md` and generated callback helper for the active node run. The supervisor downloads and verifies every ticket attachment into that run's `attachments/` directory; `START_HERE.md`, `attachments.md`, `artifacts.md`, and `context.json` expose local attachments plus tracker URLs for workflow artifacts and checkpoint provenance. The bundle also includes `publish-artifact`, which lets an agent upload any Markdown, HTML, image, PDF, JSON, YAML, text, or binary file with optional title/description/category/featured hints before its terminal callback. The durable bundle documents complete JSON schemas for comment, ask, complete, fail, and metadata callbacks. `ask` accepts one question or a batch, and every question can carry any number of suggested `options`. Batched questions are stored and answered independently while the same lease and agent conversation wait for every answer. Options are UI shortcuts only; operators always have a freeform answer field. The one-time callback reminder repeats the exact absolute assignment and helper paths so it remains actionable after context compaction.

Jira is disabled by default and needs no credentials for personal use. To enable it, set the Atlassian site/project in Configuration and provide `JIRA_EMAIL` plus `JIRA_API_TOKEN` in the tracker environment. GitHub PR observation uses `GITHUB_TOKEN`; its periodic switch and interval live in Configuration.

For a production build:

```bash
npm run build
npm start
```

The production Express process serves both the API and `dist/client`. Only one process may own a ticket root; the process lock is released during graceful shutdown and stale process locks are recovered.

At startup the tracker parses the authoritative Markdown set into an in-memory index of fully hydrated tickets. Queue, claim, lease, and metrics operations read that index instead of rescanning the directory. Every tracker mutation updates Markdown atomically and then updates the index; the filesystem watcher rebuilds it after direct external edits, so Markdown remains the sole authority. `/api/operations` exposes index generation/counts, disk availability, library validation, and background-job results. `/api/readyz` returns `503` only when required storage or libraries cannot be read or the ticket root is not writable; invalid individual tickets, prompts, or workflows produce a degraded warning while valid work remains available. `/api/healthz` remains a process-liveness probe.

`/api/capabilities` publishes the supervisor protocol version, supported workflow schema versions, and deterministic activity capabilities. Supervisor deployment checks this contract before replacing an existing daemon, so repositories must deploy the tracker before a supervisor release that requires new protocol capabilities.

All Jira and GitHub calls have a configurable `EXTERNAL_REQUEST_TIMEOUT_MS` deadline (15 seconds by default). Browser control-plane requests default to 30 seconds and attachment uploads to two minutes. Structured service logs honor `LOG_LEVEL=debug|info|warn|error`; setting `LOG_FILE` enables bounded size rotation through `LOG_MAX_BYTES` and `LOG_MAX_FILES`. The production deploy script enables file logging automatically using `DEPLOY_LOG_FILE` and retains a separate bootstrap log for pre-logger startup failures.

## Dashboard

The far-left **Inbox** page consolidates unanswered agent questions, Human Gates, blocked or failed work, assignment-delivery failures, GitHub feedback, host-local repository conflicts, and external waits near their wake/deadline. Questions, gate choices, retries, wait checks, and ticket navigation are available inline. The Queue page presents searchable ticket metadata in a table ordered by operational lifecycle: attention states, running work, ready work, drafts, then completed and cancelled tickets. Archived work is opt-in. Pending tickets use a structured Jira-style editor while preserving Markdown as the storage format. The operator selects a shared workflow or clones a ticket-specific workflow before marking work ready. After work begins, the dashboard renders the pinned graph and current node, a plain-language **what happens next** chain, state controls, PRs, agent conversations, immutable node runs, and durable activity. Taken graph edges and the current node glow; a browser-persistent route control switches between the complete graph and the routes already taken plus the expected non-failure route forward from the current node. Earlier expected routes disappear when their nodes were skipped or bypassed. Every graph node summarizes visits, wall/active time, tokens, and known cost from its durable runs; selecting a node opens an analysis view led by result, runtime, token, cost, and exact-model cards, followed by configuration, run history, telemetry, and node-scoped evidence/provenance. Incremental Herdr trace chunks are grouped into one logical trace per supervisor invocation. Browser-local state restores the active application page, selected ticket, queue filters, evidence tab/open artifact, graph zoom, and graph route view after a refresh. Invalid files expose a raw recovery editor.

Local ticket creation suggests the next atomic `AGENT-nnnn` ID. The operator may replace that suggestion with any unique nonempty ID before creation; custom and Jira-provided IDs do not consume the local sequence.

The top bar offers Light, Dark, and Retro Hacker themes. Dark preserves the original dashboard palette, Light adapts the same visual system for bright environments, and Retro Hacker uses a green phosphor terminal treatment. The selection is stored in the browser and restored on later visits.

Model selection belongs entirely to workflows. Every agent node selects a configured agent-profile alias, which resolves to a provider, exact model, and reasoning level when the workflow revision is pinned to a ticket. Tickets select workflows, inputs, and configurable stages; they do not select work or review providers. Conversation keys preserve the intended Herdr session through loops, while each node explicitly chooses whether to resume it, start fresh on every graph visit, or reset after a bounded number of visits. Provider selection never silently falls back.

The active-agent strip and ticket runtime panel show the actual workflow stage, node, resolved provider, node-scoped attempt/loss count, supervisor heartbeat, lease countdown, assignment delivery (`starting` or `running`), Herdr lifecycle state and state age, pane/workspace/tab identity, foreground cwd, terminal title, session metadata, and reported display tokens. Herdr `idle` and `done` are neutral observations: they do not produce an attention warning or advance work without a callback. A delivery failure instead closes the operational attempt without taking a workflow edge, retains its conversation identity, and automatically retries the same node twice before the third consecutive loss blocks for operator attention. When a harness exposes usage telemetry, the runtime and durable node-run views also show the exact model, reasoning setting and provenance, node-scoped uncached input/cache-read/cache-write/output/reasoning tokens, context use, rate limits, useful harness attributes, and reported USD cost. When a harness does not report cost, an exact provider/model match in the configurable pricing table may produce a clearly marked estimate; unmatched models and unknown subscription allocation remain unavailable rather than zero. Reported harness cost always wins. Every durable node run also keeps a timing ledger for wall, active, quota-paused, human-wait, and tracker-owned external-wait time. The full run array is revision-addressed beneath `TICKETS_ROOT/.runs`; ticket YAML retains only its bounded integrity reference and the API hydrates the history transparently. The ticket's **Evidence & artifacts** card defaults to a readable review packet, optionally narrows to featured or newest-per-node material, filters by node/category/media type, and supports persistent inline or fullscreen previous/next preview. Its **Provenance** tab has a per-Agent-run matrix for native harness sessions, bounded Herdr transcripts, operational traces, and execution manifests. Overall session-provenance coverage is the union of native and Herdr captures, while the Native and Herdr counts remain visible separately so a missing convenience transcript cannot be mistaken for a lost run. Low-level provenance manifests and checkpoint bundles remain available under **Technical artifacts** rather than dominating the normal review. At an active Human Gate, artifacts from the immediately preceding completed node are also presented in a focused **Review materials** card beneath the graph with the gate decisions beside them; no artifact schema is required. Evidence can be opened or downloaded without knowing its on-disk storage layout, and checkpoint creation and restoration remain available alongside the checkpoint records. A completed ticket adds an **Execution recap** with its actual workflow path, pull requests, featured evidence, interventions, elapsed/active accounting, tokens, known cost, production assessment, and provenance-capture coverage with the same source breakdown. Exhausted provider windows with a future reset are counted as quota pauses while supervisor heartbeats retain the lease; accounting automatically resumes at the reset boundary. Wait nodes instead hold no lease or supervisor capacity and durably wake a polling Script using bounded backoff, jitter, and a deadline. Completed supervisor executions link an immutable provenance manifest containing pinned identities, runtime evidence, repository before/after state, artifacts, timing, and telemetry. The ticket totals card derives token, cost, and timing rollups across every durable run and states telemetry coverage explicitly. The Operations page shows tracker readiness, Markdown-index state, storage capacity, prompt/workflow health, background maintenance results, and every reporting daemon's VM/host IP, isolated project root, Herdr session, available agents, detected Script runtimes, online state, and reserved ticket. Herdr remains the live terminal interface; immutable boundary captures are tracker-owned audit evidence, not a browser terminal emulator. Full Script output is also stored separately beneath `TICKETS_ROOT/.runs`; tickets retain a small tail and artifact digest/link.

Tracker and supervisor service logs are newline-delimited JSON. HTTP requests carry or receive `X-Request-Id`, and work lifecycle records include the available `ticket_id`, `node_id`, `lease_id`, provider, and supervisor correlation fields. Lease and artifact API failures return a stable machine-readable `code` alongside their human-readable message.

The Metrics page scans durable Markdown on demand and groups execution evidence by the ticket's original pinned workflow assignment. Its overview prioritizes completion rate, median active execution time, and median factory cost. Completion rate is `completed / (completed + failed + cancelled)`; in-progress and blocked tickets remain visible but do not count as failures. It shows node success/failure rates from all completed tickets in that cohort, branch frequencies, interruptions and lease losses, profile/model/reasoning comparisons, platform totals, and five-number distributions for duration, active time, human wait, quota pauses, tokens, cost, estimated human days, and estimated human cost. A two-arm comparison can contrast revisions of one workflow or entirely different workflows, with directional color cues for improved or regressed completion, active time, cost, token, and production metrics. Efficiency distributions use completed tickets that did not cross over to another revision; completion and production rates retain the broader settled cohort, while failed, cancelled, blocked, in-progress, and crossover counts remain visible. Date, label, workflow/revision, and production-result filters apply to both arms. A ticket may carry an optional `estimated_human_days`; the configured day rate converts that planning estimate to a human-cost baseline. Human-versus-factory savings include only completed tickets with a human estimate and complete agent-run cost coverage. Token and cost coverage is always shown; missing observations remain unavailable rather than becoming zero. Completed tickets also carry a separate, retroactively editable production assessment (`succeeded`, `failed`, `rolled_back`, `not_deployed`, or `unassessed`) that can be recorded during archival or later.

The Configuration page lists the repositories every supervisor must have and manages the default and named agent profiles used by workflow nodes. Each supervisor clones a missing repository into `PROJECT_ROOT/<repository-id>` before it can claim work. Existing paths are never pulled, reset, or replaced by this reconciliation. The Prompt Editor separately shows the agent messages, their workflow triggers, supported meta tags, and a rendered bootstrap plus durable `node.md` example.

Ready tickets also show derived repository blockers. A supervisor cannot claim a ticket while another nonterminal ticket assigned on the same hostname names any of the same repositories. Approval waits and attention states retain the reservation; completion, cancellation, or explicit release frees it. The ticket remains ready for supervisors on other hosts.

Script artifacts explicitly interpreted as `agentic-quality/v1` reports are validated by the tracker, displayed on their ticket, and aggregated by registered attribute key in completed-ticket workflow metrics. The Configuration page owns the quality registry's stable labels, types, units, direction, and numeric bounds.

## Continuous intake

The Intake page exposes campaign/source definitions, admission limits, source-run status and logs, candidate decisions, and source/campaign outcome rollups. Structured forms cover the normal campaign, runner, schedule, workflow, repository, label, readiness, and capacity fields; presets provide starting contracts and conventional script paths for New Relic, Jira, Dependabot, scheduled Scripts, and child/external work. Integration presets do not install vendor connectors—the referenced discovery script and credentials remain repository/VM configuration. Advanced YAML remains available for uncommon workflow inputs, stage overrides, and success policy. Operators can manually trigger an enabled Script source or run a safe preview while the source is disabled. A preview executes on a supervisor and validates up to 100 displayed candidates, but never admits tickets or advances the source cursor. Preview mode does not sandbox or undo external side effects, so discovery scripts should remain observational and read-only toward their source systems.

Scheduled sources execute independently on any reporting supervisor and write `{ "candidates": [...], "cursor": ... }` to `AGENTIC_INTAKE_RESULT_PATH`; the cursor from the previous successful run is available in `AGENTIC_INTAKE_CURSOR_JSON`. External systems may submit the same candidate schema without a scheduled process. Agents can emit follow-on candidates through the generated `callback emit-candidates` command, and outside assistants can use the bundled skill's `ticket emit-candidates` command. Neither path bypasses tracker admission policy.

Use a stable candidate key derived from the upstream fact, such as `new-relic:issue-42`, `dependabot:owner/repo:123`, or `dto:orders:2.4.0:consumer-b`. A source should discover facts, not decide whether capacity exists or allocate ticket IDs. Disabled campaigns/sources stop new execution and deferred admission without deleting their ledger. Source failures do not mutate or fail previously admitted tickets.

## Agent skill

[`skills/agentic-project-tracker`](skills/agentic-project-tracker) is a portable, non-MCP ticket-management skill for assistants and orchestrators. Its standard-library Python client creates and edits tickets, reads and revision-fences ticket metadata, selects published workflows and ticket-specific inputs, handles human gates and questions, monitors ticket/supervisor state, and supports Jira and GitHub follow-up. Configuration and workflow catalogs are read-only; prompt access, artifact publication, supervisor mutation, Script execution, and `/api/work/*` lease callbacks are intentionally excluded.

Install or symlink that directory into the orchestrator's normal skill directory, then configure the tracker origin:

```bash
export AGENTIC_PROJECT_TRACKER_URL=http://127.0.0.1:4310
python3 skills/agentic-project-tracker/scripts/tracker.py health
```

Run its isolated client tests with:

```bash
python3 -m unittest discover -s skills/agentic-project-tracker/tests -v
```

## Verify

```bash
npm run verify
```

The suite covers Markdown admission and preservation, versioned prompt/workflow artifacts, graph validation, typed nodes, deterministic activity allowlisting, gates and loops, duplicate rejection, external edits, atomic claims, lease/node-run fencing, routing, workflow transitions, and callback idempotency.

The optional deploy script runs `npm ci`, type-checks, and builds before stopping the managed PID. It then starts the built Express/React production service, records `.pid`, writes rotating structured output to `app.log`, and requires `/api/readyz` to succeed. It intentionally refuses broad `pkill` matching and will not stop a process whose command does not match this tracker.
